## 一、测试目的

1. 验证核心业务模块（用户、角色、菜单、部门）的主流程功能是否正确可用。
2. 验证 RBAC 权限模型在实际使用中是否真实生效（菜单可见性、按钮可用性、删除关联保护、接口鉴权）。
3. 通过反向与边界用例暴露表单校验、状态控制、会话管理中的薄弱环节。
4. 以用例集、缺陷清单、接口集合与自动化脚本，验证测试流程的完整性与可复用性。

## 三、测试范围与策略

- **P0 深度执行**：登录、用户管理、角色管理、菜单管理、部门管理。承载鉴权与组织架构主链路，正向、反向、边界用例全部执行。
- **P1 主流程执行**：字典管理、岗位管理、定时任务、在线用户。以核心 CRUD 与关键校验为主，UI 细节与极端边界仅做设计记录。

## 七、测试结论

1. **核心功能稳定**：用户、角色、菜单、部门的增删改查主流程全部通过；菜单权限分配后侧边栏按角色正常渲染（受限角色仅能看到被勾选菜单）；登录鉴权链路有效——无 token 与伪造 token 均被拒绝、连续 5 次密码错误触发 10 分钟锁定、退出后无法通过浏览器返回键恢复已登录页面。

2. **关联保护校验完整**：删除被用户引用的角色、被角色引用的菜单、含子节点的菜单与部门、已分配用户的部门，系统均正确拦截并给出明确提示；超级管理员相关角色与账号受保护，无法删除或停用。这是本次测试中表现最好的环节，也说明该项目在业务层已相当成熟。

3. **表单校验覆盖到位**：用户名称、角色名称与权限字符、菜单名称（同级）、部门名称（同级）、字典类型、岗位名称的重复校验均有效；必填项为空时可正确拦截。唯一例外是字典键值未做唯一校验（BUG-007），同一类型下可存在两条键值相同的数据项。

4. **问题集中在前后端校验一致性**：手机号格式（BUG-003）、用户名空格（BUG-004）、部门循环引用（BUG-006）三条均为「界面拦住了、接口没拦住」的同一模式——前端做了，后端缺位。这类问题在页面操作时完全看不出来，只有在接口层或批量导入路径上才会暴露，是本轮最有价值的发现方向。

5. **安全加固仍有缺口**：密码只校验长度（BUG-002，`123456` 可直接保存）；异常响应原样返回 SQL 与服务器绝对路径（BUG-009）；登录失败锁定、当前用户删除拦截、超管保护等机制则表现正常，说明安全能力建设不均衡。

6. **总体判定**：功能层面达到可用标准，权限模型有效，**未发现致命级或严重级缺陷**，阻塞上线的功能性问题为零。若部署到公网环境，建议优先补齐后端字段校验、密码策略与异常脱敏三项，再评估上线。

## 八、改进建议

| 优先级 | 建议 |
| --- | --- |
| 高 | 后端补齐手机号等字段格式校验，让表单、导入、接口三条路径共用同一套规则 |
| 高 | 统一密码策略：长度 + 字符类型组合，管理员重置与用户修改共用同一规则 |
| 高 | 全局异常处理脱敏，对外只返回固定文案，SQL 与堆栈仅写服务端日志 |
| 中 | 用户名称等关键字段入库前统一 `trim`；归属部门改为必填 |
| 中 | 部门修改增加后代校验，禁止把自身或下级设为上级 |
| 低 | 字典数据增加 `(dict_type, dict_value)` 唯一约束；导入失败提示补充 Excel 行号 |
| 低 | 多标签页登录态隔离或切换提示；定时任务删除前校验运行状态 |

## 九、遗留事项

1. 通知公告的展示入口为右上角通知铃铛，而非首页卡片；若后续版本改为首页展示，需补充一轮联动验证。
2. Postman 集合中的「强退在线用户」与「未授权角色访问受限接口」需手工填入 `offlineToken`、`lowPrivToken` 变量后执行；在线用户模块的强退结论已按接口层单独实测（`DELETE /monitor/online/{tokenId}`，强退后原令牌访问 `/getInfo` 返回 `code: 401`）。
3. 角色数据权限范围（按部门过滤数据）未验证：验证需构造跨部门、多角色账号并比对列表条数，本轮不具备该环境，该条用例已撤出，取舍见 `test-plan.md` 第九节。
4. 性能与兼容性测试未纳入本轮，后续可按需扩展。
5. 测试过程中产生的临时数据（`test05` 空格账号、`test08`、`apitest01_phone`、停用账号 `test02`、`测试删除角色`、字典项「男2」）需在提交仓库前清理，清理不影响已留存的缺陷证据截图。
